## 1. Зорилго

Лекц 2-т үзсэн чанарын хэмжүүрүүд болох latency (p90/p95), throughput (хүчин чадал), error rate (алдааны хувь)-ийг Grafana k6 хэрэгслээр бодитоор хэмжиж, ачаалал 5 → 30 → 100 VU (Virtual Users) болж өсөхөд системийн гүйцэтгэл хэрхэн өөрчлөгдөж буйг судалж дүгнэх.

---

## 2. Ёс зүйн заалт

Load тест нь зөвшөөрөлгүй хийгдвэл DoS халдлагаас ялгаагүй тул энэхүү лабораторийн бүх тестийг зөвхөн:
1. Албан ёсны дадлагын сайт: `https://test.k6.io`
2. Өөрийн локал машин дээрх Node.js сервер: `http://localhost:3101` (эх код: `server.js`)

дээр гүйцэтгэсэн бөгөөд сургуулийн болон бусад гадаад бодит вебсайт руу ямар нэгэн тест хийгээгүй.

## 3. Орчин ба k6 хувилбар

- **Үйлдлийн систем:** Ubuntu Linux (x86_64)
- **k6 хувилбар:**

k6 v2.2.0 (commit/00a9a1b7f5, go1.26.5, linux/amd64)

## 4. Скриптүүдийн бүтэц

| Файл | Тайлбар |
|---|---|
| `script.js` | Анхны baseline тест (`vus: 5`, `duration: '30s'`, stages ашиглаагүй) |
| `stages.js` | Шатлан өсгөх тест (5 → 30 → 100 → 0 VU) |
| `threshold-pass.js` | Өөрийн baseline-д үндэслэсэн `p(95)<400ms` SLO шалгалт (`test.k6.io`) |
| `threshold-fail.js` | Тестийг FAIL болгож чанарын босго (Quality Gate) харуулах зорилготой хатуу шалгалт (`p(95)<50ms`) |
| `threshold-local-pass.js` | Локал baseline (p95 11.8ms × 1.5 ≈ 18ms)-ээс гаргасан `p(95)<18ms` SLO-той тогтвортой PASS шалгалт |
| `server.js` | Локал Node.js HTTP сервер (`/` энгийн, `/slow` 100ms сааталтай) |
| `local-test.js` | Локал сервер рүү чиглэсэн ачааллын тест |
| `ai-scenario.js` | AI туслахын санал болгосон scenario бүхий тест (`group()`, хайлт, нүүр хуудас) |

> **Анхаарах зүйл:** k6 дээр `options` дотор `stages` болон `vus/duration`-ийг хамт бичвэл `stages` нь давамгайлж `vus/duration`-ийг үл тоодог тул тэдгээрийг файлуудад тусад нь салгаж зохион байгуулсан.

## 5. Ажиллуулах заавар

```bash
# 1. Түвшин тус бүрийн тестийг тусад нь ажиллуулж гаралтыг хадгалах
mkdir -p results
k6 run --vus 5 --duration 1m script.js | tee results/run-05vu.txt
k6 run --vus 30 --duration 1m script.js | tee results/run-30vu.txt
k6 run --vus 100 --duration 1m script.js | tee results/run-100vu.txt

# 2. Шатлан өсгөх (stages) тестийг ажиллуулах
k6 run stages.js | tee results/run-stages.txt

# 3. Threshold (SLO) PASS ба FAIL гаралтуудыг турших
k6 run threshold-pass.js | tee results/threshold-pass.txt
k6 run threshold-fail.js | tee results/threshold-fail.txt

# 4. Локал серверийг асааж найдвартай PASS тест хийх
node server.js &
k6 run threshold-local-pass.js | tee results/threshold-local-pass.txt

# 5. AI туслахын санал болгосон scenario тестийг ажиллуулах
k6 run ai-scenario.js | tee results/run-ai-scenario.txt
```

## 7. SLO (Thresholds) ба түүнийг сонгосон үндэслэл

Анхны 5 VU baseline хэмжилтээр `test.k6.io` сайтын p95 хугацаа **263.48 ms** гарсан. Тиймээс зааврын жишээ тоог хуулалгүй, өөрийн хэмжсэн baseline утгыг 1.5 дахин авч дээш бүхэлчлэн **SLO-г `p(95) < 400ms`** гэж тодорхойлсон (263.48 × 1.5 ≈ 395 ms). Энэхүү 1.5 дахин коэффициент нь интернэтийн жирийн хэлбэлзлийг даах зай үлдээхийн зэрэгцээ серверийн бодит удаашралыг цаг алдалгүй илрүүлэх боломжийг олгодог бөгөөд `error rate < 1%` нь лекцийн availability зорилтод нийцнэ. Локал серверийн хувьд мөн өөрийн хэмжилтээс гаргасан: локал baseline p95 **11.8 ms** × 1.5 ≈ 18 ms тул локал SLO-г **`p(95) < 18ms`** гэж тавьсан.

- **PASS гаралт:** `results/threshold-local-pass.txt` — Локал сервер дээр хэмжсэн p95 нь 2.47 ms гарч `< 18ms` нөхцөлийг бүрэн хангаж амжилттай PASS гарсан.
- **FAIL гаралт:** `results/threshold-fail.txt` — Санаатайгаар хатуу `p(95) < 50ms` босго тавихад бодит p95 нь 476.28 ms болж, `thresholds on metrics 'http_req_duration' have been crossed` гэсэн алдаа заан FAIL болж, CI/CD pipeline дээр чанаргүй кодыг зогсоодог механизмыг баталсан.
- **Нэмэлт тайлбар (нуулгүй бичив):** 5 VU-г 1 минутаар тусад нь дахин ажиллуулахад (`results/run-05vu.txt`) p95 нь 1.14 s хүрч 400 ms SLO-г зөрчсөн. Энэ нь тухайн хэмжилтийн цонхны сүлжээний ачаалал ихэссэнтэй холбоотой (өмнөх давталтууд 263–488 ms хэлбэлзэж байсан) бөгөөд гадаад сүлжээний хэлбэлзэл дангаараа threshold шийдвэрийг эргүүлж чаддагийг харуулж байна. Иймээс найдвартай PASS үр дүнг baseline-аас нь гаргасан 18 ms SLO-той локал серверээр давхар баталгаажуулсан.

## 8. Дүгнэлт

Гурван түвшинг тус бүрд нь 1 минутаар туршихад throughput нь 4.47-өөс 41.42 ба 110.33 req/s болж, p95 latency нь 1.14 s, 545.66 ms болон 1.17 s гарлаа. 5 VU хэмжилт нь сүлжээний ачаалал ихтэй цонхонд таарч p95 нь 30 VU-ээс өндөр гарсан нь алсын серверийн хэлбэлзэл түвшин хоорондын шууд харьцуулалтад хүртэл нөлөөлдгийг харуулж байна. Гэсэн хэдий ч 30-аас 100 VU рүү өсгөхөд throughput 41.42-оос 110.33 req/s болж өссөн бол p95 545.66 ms-ээс 1.17 s болж муудсан нь Лекц 2-т үзсэн "хүчин чадал өсөхөд tail latency уртасна" гэсэн онолын зөрчлийг бодит хэмжилтээр баталж байна. Бүх гурван түвшинд error rate 0.00% буюу ямар ч хүсэлт унаагүй тул системийн availability хэвийн хадгалагдаж чадсан. Шатлан өсгөх stages тест нь ерөнхий нэгдсэн ганц summary (p95 1.5 s) өгдөг тул түвшин бүрийн онцлогийг нарийн харахын тулд тусдаа ажиллуулах шаардлагатайг туршилтаар ойлголоо. Анхны baseline (p95 263.48 ms)-ээс гаргасан p(95) < 400 ms SLO нь 1 минутын 5 VU (1.14 s), 30 VU (545.66 ms) болон 100 VU (1.17 s) хэмжилтүүдэд зөрчигдсөн нь муудсан сүлжээний нөхцөлд хэрэглэгчийн туршлага бүх түвшинд доройтож буйг харуулж байна. Харин локал baseline (p95 11.8 ms)-ээс гаргасан p(95) < 18 ms SLO нь p95 2.47 ms-ээр тогтвортой хангагдсан тул найдвартай PASS үр дүнг локал орчинд шалгах нь хамгийн зөв арга болохыг харлаа. Санаатайгаар хатуу тавьсан p(95) < 50 ms шалгалт нь амжилттай FAIL болж, автоматжуулсан CI чанарын босго (Quality Gate) хэрхэн ажилладгийг бүрэн нотоллоо. Дүгнэж хэлэхэд, гүйцэтгэлийн тестийн SLO нь зохиомол тоо биш, харин бодит baseline хэмжилтэд (гадаад болон локал орчин тус бүрдээ) суурилсан үед л жинхэнэ чанарын хэмжүүр болж чадна.

## 10. Нэмэлт даалгавар: AI туслахын k6 скриптийн шинжилгээ

AI туслахаар (ChatGPT/Claude) хэрэглэгчийн нэвтрэх болон хайлт хийх зан төлөвийг дуурайсан k6 скрипт үүсгүүлж туршив (`ai-scenario.js`). AI анх санал болгохдоо бодит бус эсвэл зөвшөөрөлгүй гадаад хаяг руу POST хүсэлт илгээх кодоор үүсгэсэн тул ёс зүйн заалтын дагуу зөвхөн зөвшөөрөгдсөн `https://test.k6.io` домэйн болон GET хүсэлт рүү гараар засаж ажиллуулах шаардлагатай болсон. AI-ийн санал болгосон `group()` бүтэц болон шатлан өсгөх `stages` нь хэрэглэгчийн бодит алхмуудыг логик дараалалд оруулахад тун ойлгомжтой, сайн шийдэл байв. Гэвч AI нь манай байршлын сүлжээний бодит хоцролтыг (TLS handshake 100-200ms) мэдэхгүй тул `p(95) < 200ms` гэсэн хэт өөдрөг, бодит бус threshold санал болгосныг baseline хэмжилтдээ тулгуурлан засав. Миний өмнө бичсэн энгийн скрипттэй харьцуулахад AI скрипт нь `group()` ашигласнаараа алхам бүрийг салгаж харахад давуу талтай байсан. Харин бай URL-ын ёс зүйн аюулгүй байдал болон хэмжилтийн бодит baseline дээр үндэслэсэн SLO босгыг зөв сонгох тал дээр инженер хүний хяналт заавал дутагдаж байлаа.
