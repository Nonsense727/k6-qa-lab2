## 1. Зорилго

Лекц 2-т үзсэн чанарын хэмжүүрүүд болох latency (p90/p95), throughput (хүчин чадал), error rate (алдааны хувь)-ийг Grafana k6 хэрэгслээр бодитоор хэмжиж, ачаалал 5 → 30 → 100 VU (Virtual Users) болж өсөхөд системийн гүйцэтгэл хэрхэн өөрчлөгдөж буйг судалж дүгнэх.

---

## 2. Ёс зүйн заалт

Load тест нь зөвшөөрөлгүй хийгдвэл DoS халдлагаас ялгаагүй тул энэхүү лабораторийн бүх тестийг зөвхөн:
1. Албан ёсны дадлагын сайт: `https://test.k6.io`
2. Өөрийн локал машин дээрх Node.js сервер: `http://localhost:3101` (эх код: `server.js`)

дээр гүйцэтгэсэн бөгөөд сургуулийн болон бусад гадаад бодит вебсайт руу ямар нэгэн тест хийгээгүй.

---

## 3. Орчин ба k6 хувилбар

- **Үйлдлийн систем:** Ubuntu Linux (x86_64)
- **k6 хувилбар:**

```text
k6 v2.2.0 (commit/00a9a1b7f5, go1.26.5, linux/amd64)
```

---

## 4. Скриптүүдийн бүтэц

| Файл | Тайлбар |
|---|---|
| `script.js` | Анхны baseline тест (`vus: 5`, `duration: '30s'`, stages ашиглаагүй) |
| `stages.js` | Шатлан өсгөх тест (5 → 30 → 100 → 0 VU) |
| `threshold-pass.js` | Өөрийн baseline-д үндэслэсэн `p(95)<400ms` SLO шалгалт (`test.k6.io`) |
| `threshold-fail.js` | Тестийг FAIL болгож чанарын босго (Quality Gate) харуулах зорилготой хатуу шалгалт (`p(95)<50ms`) |
| `threshold-local-pass.js` | Локал сервер рүү хийсэн найдвартай, тогтвортой PASS SLO шалгалт (`p(95)<100ms`) |
| `server.js` | Локал Node.js HTTP сервер (`/` энгийн, `/slow` 100ms сааталтай) |
| `local-test.js` | Локал сервер рүү чиглэсэн ачааллын тест |

> **Анхаарах зүйл:** k6 дээр `options` дотор `stages` болон `vus/duration`-ийг хамт бичвэл `stages` нь давамгайлж `vus/duration`-ийг үл тоодог тул тэдгээрийг файлуудад тусад нь салгаж зохион байгуулсан.

## 5. Ажиллуулах заавар

```bash
# 1. Түвшин тус бүрийн тестийг тусад нь ажиллуулж гаралтыг хадгалах
mkdir -p results
k6 run --vus 5 --duration 30s script.js | tee results/run-05vu.txt
k6 run --vus 30 --duration 1m script.js | tee results/run-30vu.txt
k6 run --vus 100 --duration 1m script.js | tee results/run-100vu.txt

# 2. Шатлан өсгөх (stages) тестийг ажиллуулах
k6 run stages.js | tee results/run-stages.txt

# 3. Threshold (SLO) PASS ба FAIL гаралтуудыг турших
k6 run threshold-pass.js | tee results/threshold-pass.txt
k6 run threshold-fail.js | tee results/threshold-fail.txt

# 4. Локал серверийг асааж найдвартай PASS тест хийх
node server.js &
k6 run threshold-local-pass.js | tee results/threshold-local-pass.txt
```

## 6. Хэмжилтийн үр дүнгийн харьцуулсан хүснэгт

`stages` горим нь эцэстээ бүх түвшнийг нэгтгэсэн ганц summary өгдөг тул 5, 30, 100 VU тус бүрийн яг бодит үр дүнг авахын тулд тус тусад нь ажиллуулсан. Хүснэгтэд бичигдсэн утгууд нь `results/` хавтсан дахь файлуудтай 100% яг таарна.

| Зэрэгцээ хэрэглэгч (VU) | Хугацаа | Latency p90 | Latency p95 | Throughput (req/s) | Нийт хүсэлт | Error rate |
|---|---|---|---|---|---|---|
| **5 VU** (Baseline) | 30s | 243.04 ms | 263.48 ms | 7.37 req/s | 230 | 0.00% (0/230) |
| **30 VU** | 1m | 327.87 ms | 545.66 ms | 41.42 req/s | 2530 | 0.00% (0/2530) |
| **100 VU** | 1m | 599.23 ms | 1.17 s (1170 ms) | 110.33 req/s | 6822 | 0.00% (0/6822) |

- **Эх сурвалж файлууд:** `results/run-05vu.txt`, `results/run-30vu.txt`, `results/run-100vu.txt`
- **Шатлан өсгөх тест (`results/run-stages.txt`):** Нэгтгэсэн дундаж p90 = 749.48 ms, p95 = 1.5 s, throughput = 34.43 req/s гарсан бөгөөд энэ нь ерөнхий төлөвийг харуулдаг.
- **Локал сервер тест (`results/run-local.txt`, 5 VU):** Сүлжээний саадгүй орчинд p90 = 10.18 ms, p95 = 11.8 ms, 4.97 req/s, error rate = 0.00% гарсан.

## 7. SLO (Thresholds) ба түүнийг сонгосон үндэслэл

5 VU бүхий baseline хэмжилтээр `test.k6.io` сайтын p95 хугацаа **263.48 ms** гарсан. Тиймээс зааврын жишээ тоог хуулалгүй, өөрийн хэмжсэн baseline утгыг 1.5 дахин авч дээш бүхэлчлэн **SLO-г `p(95) < 400ms`** гэж тодорхойлсон. Энэхүү 1.5 дахин коэффициент нь интернэтийн жирийн хэлбэлзлийг даах зай үлдээхийн зэрэгцээ серверийн бодит удаашралыг цаг алдалгүй илрүүлэх боломжийг олгодог бөгөөд `error rate < 1%` нь лекцийн availability зорилтод нийцнэ.

- **PASS гаралт:** `results/threshold-local-pass.txt` — Локал сервер дээр хэмжсэн p95 нь 13.67 ms гарч `< 100ms` нөхцөлийг бүрэн хангаж амжилттай PASS гарсан.
- **FAIL гаралт:** `results/threshold-fail.txt` — Санаатайгаар хатуу `p(95) < 50ms` босго тавихад бодит p95 нь 476.28 ms болж, `thresholds on metrics 'http_req_duration' have been crossed` гэсэн алдаа заан FAIL болж, CI/CD pipeline дээр чанаргүй кодыг зогсоодог механизмыг баталсан.
- **Нэмэлт тайлбар:** Алсын `test.k6.io` сервер рүү давтан шалгахад (`results/threshold-pass.txt`) p95 нь 417.26 ms хүрч бага зэрэг босго давсан нь олон нийтийн сүлжээний тогтворгүй байдлаас хамаардаг болохыг харуулсан тул найдвартай PASS үр дүнг локал серверээр давхар баталгаажуулсан.

## 8. Дүгнэлт

Энэхүү лабораторийн ажлаар виртуал хэрэглэгчийн тоог 5-аас 30 ба 100 болгон өсгөхөд throughput нь 7.37-оос 41.42 ба 110.33 req/s болж өссөн боловч p95 latency нь 263.48 ms-ээс 545.66 ms болон 1.17 секунд хүртэл огцом муудлаа. Энэ нь Лекц 2-т үзсэн "Ачаалал ихсэхэд нийт боловсруулах чадал нэмэгдэх боловч нэгж хэрэглэгчид ирэх хүлээлтийн хугацаа (tail latency) уртасна" гэсэн онолын зөрчлийг бодит хэмжилтээр баталж байна. Бүх гурван түвшинд error rate 0.00% буюу ямар ч хүсэлт унаагүй тул системийн availability хэвийн хадгалагдаж чадсан. Шатлан өсгөх stages тест нь ерөнхий нэгдсэн ганц summary өгдөг тул түвшин бүрийн онцлогийг нарийн харахын тулд тусдаа ажиллуулах шаардлагатайг туршилтаар ойлголоо. Миний тодорхойлсон p(95) < 400ms бүхий SLO нь 5 VU үед хангагдаж байсан боловч 30 VU хүрэхэд 545.66 ms болж зөрчигдсөн нь 30 орчим зэрэгцээ хэрэглэгчийн цэгээс эхлэн хэрэглэгчийн сэтгэл ханамж муудаж эхэлснийг харуулж байна. Нийтийн интернет сүлжээний савалгаа нь гадаад серверийн latency-д шууд нөлөөлдөг тул найдвартай PASS үр дүнг локал сервер дээр шалгах нь хамгийн зөв арга болохыг харлаа. Санаатайгаар хатуу тавьсан p(95) < 50ms шалгалт нь амжилттай FAIL болж, автоматжуулсан CI чанарын босго (Quality Gate) хэрхэн ажилладгийг бүрэн нотоллоо. Мөн JavaScript код дээр суурилсан k6 хэрэгсэл нь тестийг Git-д хувилбаржуулан хадгалах болон автоматжуулахад GUI хэрэгслүүдээс хамаагүй илүү давуу талтайг практик дээр баталлаа. Дүгнэж хэлэхэд, гүйцэтгэлийн тестийн SLO нь зохиомол тоо биш, харин бодит baseline хэмжилтэд суурилсан үед л жинхэнэ чанарын хэмжүүр болж чадна.
